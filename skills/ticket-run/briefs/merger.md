# Merger brief

You merge one reviewed ticket branch of the run sheet's repo into the feature branch `<feature branch>`, in its worktree `<feature worktree>` (the orchestrator fills both from the run sheet). The sheet (your prompt names it) holds this repo's facts in its `## Repo facts` section; "the sheet's <fact>" below means that entry. You never change a ticket or the notes repo, never open a browser, never merge the pull request, never rebase the feature branch, never push `main`, never force-push. Change files with Edit or Write, never from Bash (`cat >`, `python - <<`, `sed -i`): a hook blocks it. A fix you must make inside the merge commit (the pre-commit hook refuses it otherwise) is named in the merge message and your reply. Commit messages never name a ticket (its number or a notes-repo path): only the maintainer uses the tickets, and the rest of the team reading the repo's history doesn't know them. Say what changed instead.

Steps:
1. `git -C <feature worktree> status --short` must be clean, and `git -C <feature worktree> fetch origin` run; HEAD matches `origin/<feature branch>`. Where the sheet's Database has one, reset the feature worktree's database as it says, so the checks run on a fresh one, in a command of its own (a refused command takes the rest of its line with it). If the reset is refused (an auto-mode classifier may refuse dropping a database), don't retry it or route around it: where the sheet says the tests truncate, run the checks unreset and say so in your reply. Touch no other database.
2. Merge: `git -C <feature worktree> merge --no-ff <ticket branch> -m "Merge <ticket branch>: <what it adds, in plain words>"` (for example `Merge orders-04-refunds: refund a paid order from its page`; the message's second paragraph: one line on what landed; end with a blank line then `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`). If git adds a `# Conflicts:` trailer, amend the message without it before pushing.
3. Conflicts: load the `resolving-merge-conflicts` skill and resolve each hunk with Edit, only where the two sides' intent makes it unambiguous (both tickets' files are in the message). Generated files, lockfiles and migrations: as the sheet's Generated files says, and say in your report what you did. A conflict you cannot settle from the two intents: `git merge --abort`, and report it with both sides quoted.
4. Install per the sheet's Install if the lockfile changed (an install-script approval prompt: stop and report). Then the sheet's Checks in full (the test run as a background task; wait for its notification, not Monitor, and start no polling loop such as `until grep …` as a background task: it outlives your reply and keeps you open). If one fails for a reason the merge created (two tickets touching the same file), fix it in a follow-up commit on the feature branch with a message that says so; if it fails for a reason inside one ticket, stop and report, leaving the merge in place but unpushed.
5. Push: `timeout 60 git -C <feature worktree> push origin <feature branch>`, foreground; if it stalls, run it again, up to five tries. Confirm with `git -C <feature worktree> ls-remote origin <feature branch>` that the remote tip matches HEAD.
6. If the message names checks to confirm after the merge (a seam), check each on the merged code and say what you found; do not fix it unless the message says to.
7. Reply in at most ten lines: the merge commit's full SHA and any follow-up commits, the check results (test count, failures), what you did about generated files, lockfile and migrations, each named check's result, and any finding.
